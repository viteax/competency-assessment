# Развёртывание на сервере

Инструкция для того, кто будет обслуживать систему. Всё работает в Docker: приложение,
PostgreSQL, Caddy (HTTPS) и ежедневные резервные копии.

## 1. Требования

- Linux-сервер (Ubuntu 22.04+, Debian 12+ или аналог), 1–2 ядра, 2 ГБ памяти, 10 ГБ диска.
- Docker 24+ с плагином Compose: `docker compose version`.
- Один из вариантов доступа:
  - **публичный домен** (например, `tests.example.ru`), DNS-запись указывает на сервер, открыты
    порты 80 и 443 – HTTPS-сертификат Let's Encrypt Caddy получит и будет продлевать сам;
  - **сервер за прокси вуза**, который уже обеспечивает HTTPS, – тогда открыт только порт 80.

> Без HTTPS пароли идут по сети открытым текстом. Режим «только HTTP» допустим, только если
> HTTPS делает прокси перед сервером.

## 2. Установка

```bash
git clone https://github.com/viteax/competency-assessment.git /opt/competency
cd /opt/competency
cp .env.example .env
```

Заполните в `.env` три обязательных значения:

```bash
SITE_ADDRESS=tests.example.ru   # или :80 за прокси вуза
SECRET_KEY=...                  # python3 -c "import secrets; print(secrets.token_urlsafe(48))"
POSTGRES_PASSWORD=...           # любой длинный случайный, например так же через secrets
```

Права на файл: `chmod 600 .env` – в нём секреты.

## 3. Первый запуск

```bash
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml ps      # все сервисы – running / healthy
```

`--build` собирает образ на сервере из исходников. Если образ опубликован в GitHub Container
Registry, можно не собирать: укажите в `.env` `APP_IMAGE=ghcr.io/viteax/competency-assessment:2.0.0`
и запускайте без `--build`.

Миграции базы применяются автоматически при старте приложения.

**Создайте администратора** (пароль спросит интерактивно):

```bash
docker compose -f docker-compose.prod.yml exec api python -m scripts.create_admin <логин>
```

Откройте `https://<домен>/` и войдите. Студентов удобнее всего загрузить во вкладке
«Импорт → Студенты»: система выдаст временные пароли, которые студенты сменят при первом входе.

> Демо-данные (`scripts.seed`) в продакшене загрузить нельзя – сервер откажется: у демо-учёток
> публичные пароли.

## 4. Проверка работы

```bash
curl -fsS https://<домен>/ready     # {"status":"ok","version":"2.0.0"} – приложение и база в порядке
curl -fsS https://<домен>/health    # процесс жив (базу не проверяет)
```

Для внешнего мониторинга (UptimeRobot, Zabbix и т.п.) проверяйте `/ready` раз в минуту.

## 5. Логи

```bash
docker compose -f docker-compose.prod.yml logs -f api      # приложение
docker compose -f docker-compose.prod.yml logs -f caddy    # прокси и HTTPS
docker compose -f docker-compose.prod.yml logs backup      # резервные копии
```

Логи приложения – JSON, по строке на запрос: метод, путь, статус, время ответа, пользователь,
IP и `request_id`. Если пользователь видит «внутренняя ошибка сервера, код запроса …», найдите
подробности по этому коду:

```bash
docker compose -f docker-compose.prod.yml logs api | grep <код>
```

Логи ротируются автоматически (до 5 файлов по 20 МБ на сервис). Действия пользователей
(кто что изменил) хранятся отдельно – во вкладке «Журнал» у администратора.

## 6. Резервные копии

Сервис `backup` каждый день в `BACKUP_TIME` (по умолчанию 03:30, часовой пояс `TZ`) делает
копию базы в `./backups/competency-ГГГГ-ММ-ДД_ЧЧММ.dump`, проверяет, что она читается, и удаляет
копии старше `BACKUP_KEEP_DAYS` дней (по умолчанию 30).

**Копия прямо сейчас** (например, перед обновлением):

```bash
docker compose -f docker-compose.prod.yml exec backup sh /usr/local/bin/backup.sh
```

**Храните копии не только на этом сервере.** Копии в `./backups` не спасут при поломке диска.
Настройте регулярное копирование папки на другой сервер или в хранилище, например:

```bash
# crontab -e на сервере: каждый день в 04:00 – на резервный сервер
0 4 * * * rsync -a --delete /path/to/competency-assessment/backups/ backup@other-host:/backups/competency/
```

**Восстановление** (заменит текущие данные; перед этим скрипт сам сделает свежую копию):

```bash
deploy/restore.sh backups/competency-2026-10-13_0330.dump
```

Раз в семестр проверяйте восстановление на тестовой машине – непроверенная копия может
оказаться бесполезной в нужный момент.

## 7. Обновление

```bash
cd /opt/competency
docker compose -f docker-compose.prod.yml exec backup sh /usr/local/bin/backup.sh   # копия
git pull
docker compose -f docker-compose.prod.yml up -d --build
```

При использовании готового образа вместо `git pull` и `--build` поменяйте версию в `APP_IMAGE`
и выполните `docker compose -f docker-compose.prod.yml up -d`. Миграции применятся при старте.
Что изменилось в версии – в [CHANGELOG.md](../CHANGELOG.md).

**Откат:** верните предыдущую версию образа (или `git checkout <тег>` и `--build`). Если новая
версия успела изменить схему базы, восстановите копию, сделанную перед обновлением.

## 8. Демо-стенд

Копия системы с выдуманными данными и публичными демо-учетками – показать, как все устроено,
не пуская в прод. Работает на том же сервере рядом с продом: своя база, общий только Caddy.
Код лежит рядом с копией прода, в папке с суффиксом `-demo` (`/opt/competency-demo`).

Демо поднимает скрипт настройки из раздела 9. Вручную – так:

```bash
git clone https://github.com/viteax/competency-assessment.git /opt/competency-demo
SSH_ORIGINAL_COMMAND=demo sh /opt/competency/deploy/remote-deploy.sh   # сборка на месте, запуск, демо-данные
```

Адрес демо – отдельный файл для Caddy прода (в git его нет, у каждого сервера свой):

```bash
cat > /opt/competency/deploy/sites/demo.caddy <<'CADDY'
demo.example.ru {
	reverse_proxy demo-api:8000
}
CADDY
cd /opt/competency && docker compose -f docker-compose.prod.yml restart caddy
```

Без своего домена подойдет адрес вида `demo.<IP сервера>.sslip.io`: он сам указывает на сервер,
и Caddy получит для него сертификат.

> На демо пароли публичные (`admin` / `admin123`): любой, у кого есть ссылка, войдет
> администратором. Реальные данные туда не загружайте. Сбросить демо к исходному состоянию:
> `docker compose -f docker-compose.demo.yml down -v`, затем снова `remote-deploy.sh` (см. выше).

## 9. Автоматическое обновление (CD)

После настройки ниже GitHub Actions обновляет сервер сам:

- **пуш в `main`** (после зеленых проверок CI) – демо-стенд переходит на этот коммит и его
  образ `ghcr.io/viteax/competency-assessment:sha-<коммит>`, собранный и проверенный в CI
  (на сервере ничего не собирается);
- **тег `v1.2.3`** – прод: резервная копия, затем образ `ghcr.io/viteax/competency-assessment:1.2.3`
  из GitHub Container Registry, перезапуск, миграции при старте. Если в окружении `prod`
  включено подтверждение, обновление ждет нажатия кнопки в GitHub.

### Выпуск версии

Все изменения по ходу работы записываются в `CHANGELOG.md` в раздел «Не выпущено». Выпуск –
это перенос этих записей в раздел версии и тег. Номер – по [SemVer](https://semver.org/lang/ru/):
только исправления – последняя цифра (2.0.1 → 2.0.2), новые возможности – средняя
(2.0.2 → 2.1.0), несовместимые изменения API или данных – первая (2.1.0 → 3.0.0).

**Кнопкой (обычный способ)**, когда CI на последнем коммите `main` зеленый:

1. Actions → **Release** → **Run workflow** → номер версии, например `2.0.2` → **Run workflow**.
   Кнопка сама переносит «Не выпущено» в раздел версии, меняет версию в `pyproject.toml`
   и `uv.lock` и пушит коммит «Release 2.0.2» в `main` (если это уже сделано вручную –
   пропускает шаг), ставит тег `v2.0.2`, публикует релиз с разделом из `CHANGELOG.md`
   и запускает CI на теге. Пустой раздел «Не выпущено», уже выпущенный или не новый номер –
   ошибка, ничего не меняется.
2. Actions → запуск **CI** на `v2.0.2` → после тестов и сборки образа **Review deployments**
   → `prod` → **Approve and deploy**. Задача `deploy-prod` сделает резервную копию, обновит
   прод и проверит `/ready`.

**Вручную** – то же самое из копии репозитория на своем компьютере:

```bash
git pull
uv run python -m scripts.release 2.0.2    # версия в pyproject.toml и uv.lock, раздел в CHANGELOG
git diff                                  # проверить, что попало в выпуск
git commit -am "Release 2.0.2" && git push
```

Когда CI на коммите станет зеленым – тег: кнопкой Release с тем же номером, на странице
Releases (**Draft a new release** → тег `v2.0.2`, Target `main`) или
`git tag -a v2.0.2 -m 2.0.2 && git push origin v2.0.2`. Дальше – подтверждение, как в шаге 2.
С сервера тег не ставьте: у него нет прав на запись в GitHub.

Если CI по тегу упал до деплоя, прод не тронут: исправьте ошибку и выпустите следующую версию
(2.0.3) – переставлять уже опубликованный тег не нужно.

### Настройка (один раз)

**1. На сервере** – в копии прода, когда прод уже работает (разделы 2–3):

```bash
cd /opt/competency && git pull
sudo sh deploy/setup-cd.sh demo.example.ru
```

Скрипт поднимает демо-стенд и дает ему адрес в Caddy, создает ключ деплоя и печатает значения
для GitHub. Ключ разрешает только запуск `deploy/remote-deploy.sh` (`restrict,command=...`
в `/root/.ssh/authorized_keys`), shell на сервере он не открывает. Приватный ключ скрипт нигде
не сохраняет – он есть только в выводе. Если сервер за NAT, вторым аргументом укажите внешний IP,
по которому к нему подключаются. Повторный запуск безопасен и заменяет ключ новым.

**2. В GitHub** – Settings → Secrets and variables → Actions, значения из вывода скрипта:

| Тип | Имя | Значение |
| :-- | :-- | :-- |
| Secret | `DEPLOY_SSH_KEY` | приватный ключ деплоя – длинная строка base64 |
| Secret | `DEPLOY_KNOWN_HOSTS` | ключ сервера – защита от подмены сервера |
| Variable | `DEPLOY_HOST` | IP или домен сервера |
| Variable | `PROD_URL` | `https://<домен прода>` – проверка `/ready` после обновления |
| Variable | `DEMO_URL` | `https://<домен демо>` |

Без `DEPLOY_HOST` задачи деплоя пропускаются, CI работает как раньше.

**3. Подтверждение прода** (рекомендуется): Settings → Environments → `prod` →
Required reviewers – добавить себя и сохранить. Создайте окружение заранее (New environment),
тогда подтверждение действует уже с первого деплоя.

Образ в GHCR уже публичный, сервер скачивает его без входа.

**Проверка:** любой пуш в `main` – в Actions появится задача `deploy-demo`. Прод – после первого
тега.

**Откат прода** – перезапустить («Re-run») задачу деплоя предыдущего тега в GitHub Actions или
на сервере: `SSH_ORIGINAL_COMMAND="prod 1.2.2" sh deploy/remote-deploy.sh`. Если новая версия
успела изменить схему базы, восстановите копию, сделанную перед обновлением (раздел 6). На версии
до 2.0.0 автоматического обновления не было, на них откатывайте вручную (раздел 7): скрипт такие
версии не примет, иначе ключ деплоя перестал бы работать.

## 10. Чек-лист безопасности

- [ ] Сайт открывается по `https://`, в браузере нет предупреждений о сертификате.
- [ ] `.env` с правами 600, не попадает в git и в общие папки.
- [ ] Открыты только нужные порты (80/443); порты базы (5432) и приложения (8000) снаружи
      недоступны – так настроено в compose, не меняйте.
- [ ] Администраторов – минимум, у каждого своя учётка (видно в журнале, кто что делал).
- [ ] Копии из `./backups` регулярно уходят на другой сервер.
- [ ] Обновления системы и Docker на сервере ставятся регулярно.

## 11. Решение проблем

| Симптом | Причина и решение |
| :-- | :-- |
| `api` перезапускается, в логах `задайте SECRET_KEY` | В `.env` нет `SECRET_KEY` или он короче 32 символов. |
| В логах `у демо-учёток публичные пароли` | В базу загружали демо-данные. Удалите учётки admin/student1–3 или смените им пароли (через dev-окружение) либо восстановите чистую копию. |
| Caddy не получает сертификат | DNS-запись не указывает на сервер или закрыты порты 80/443. Смотрите `logs caddy`. |
| `/ready` отвечает 503 | Приложение не достучалось до базы: `logs db`, свободное место на диске (`df -h`). |
| Пользователь: «несколько неверных паролей подряд» | Защита от подбора: подождать 30 секунд. Забытый пароль администратор сбрасывает во вкладке «Студенты». |
| Пользователя выкидывает на страницу входа | Сессия завершается после 60 минут без действий (`SESSION_IDLE_MINUTES`). |
