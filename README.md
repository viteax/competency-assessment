# Competency Assessment

Сервис тестирования студентов по компетенциям ФГОС (УК, ОПК, ПК) с привязкой
результатов к трудовым функциям профстандарта (например, 06.001 «Программист»).

## Идея

```
Учебный план ─► Дисциплины ─► Компетенции (УК / ОПК / ПК) ─► Индикаторы
                                    │
                                    ├─► Банк вопросов ─► Тест ─► Назначение группе ─► Попытка студента
                                    │
Профстандарт ─► ОТФ ─► ТФ ◄─────────┘  (ТФ ⇒ ПК: какие компетенции нужны для трудовой функции)
```

1. **Администратор** собирает тест на остаточные знания: выбирает группу и семестр, в котором
   она сейчас (по году набора подставляется сам). Система показывает только дисциплины,
   завершённые до этого семестра (по учебному плану), и компетенции, которые они формируют.
   Вопросы берутся только из завершённых дисциплин, по N на компетенцию, равномерно по
   индикаторам.
2. Тест собирается в нескольких **вариантах**, которые не пересекаются по вопросам: 20 вопросов
   на компетенцию при N = 5 — 4 варианта. Название теста любое, но уникальное.
3. Тест назначается **группе** — новый или уже собранный, чтобы у разных групп были одни и те
   же вопросы и результаты можно было сравнивать. Во вкладке «Тесты» видны варианты с вопросами
   и кто сколько прошёл; тест можно снять с группы или удалить, пока его никто не открывал.
4. **Студент** проходит тест и получает балл (например, 5/6). Ему достаётся случайный вариант
   из выданных реже всего, порядок вопросов и ответов перемешан.
5. По результатам строятся отчёты:
   - доля верных ответов по каждой компетенции (порог «сформирована» по умолчанию 60%,
     администратор меняет его в «Справочники → Настройки»);
   - **ПК → ОТФ**: какие трудовые функции профстандарта студент закрывает. ТФ закрыта,
     если сформированы все связанные с ней компетенции, ОТФ — если закрыты все её ТФ;
   - **выгрузка в Excel** по группе (все тесты или один): ФИО, группа, дата тестирования,
     «N из M» по каждой компетенции с цветом «сформирована / нет», отдельный лист — уровни
     трудовых функций;
   - **выгрузка в Word** по образцу фонда оценочных материалов — собранный тест (по
     вариантам) и ФОМ дисциплины, бланк и отдельно ключ с ответами;
   - **«роза ветров»** по группе (среднее) или студенту: уровень компетенций и трудовых функций
     на шкале 0–5, с выгрузкой в PNG. Уровень ТФ — среднее по её проверенным компетенциям.

## Стек

Python 3.12 (uv), FastAPI, SQLAlchemy 2, PostgreSQL, Pydantic 2, Pytest.

## Запуск

**На сервере (продакшен)** — [docs/deploy.md](docs/deploy.md): Docker Compose с PostgreSQL,
автоматическим HTTPS (Caddy) и ежедневными резервными копиями.

**Локально для разработки и демо:**

```bash
docker compose up --build
docker compose exec api python -m scripts.seed   # демо-данные
```

Веб-интерфейс: http://localhost:8000/ · документация API: http://localhost:8000/docs (кнопка **Authorize** — вход по логину и паролю).

Демо-учётки из `seed` (только в режиме разработки): `admin` / `admin123`,
`teacher` / `teacher123` (преподаватель), `student1`…`student3` / `student123`. Для реальной эксплуатации — раздел
[«Безопасность»](#безопасность).

Локально без Docker — через [uv](https://docs.astral.sh/uv/getting-started/installation/)
(он сам поставит Python 3.12 и зависимости точно по `uv.lock`):

```bash
uv sync
export ENVIRONMENT=dev                 # по умолчанию строгий режим prod
export DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/competency
uv run python -m scripts.seed          # применяет миграции и заполняет демо-данными
uv run uvicorn app.main:app --reload
```

Без PostgreSQL можно хранить всё в файле SQLite — удобно для демонстрации:

```bash
export ENVIRONMENT=dev DATABASE_URL=sqlite:///./competency.db
# PowerShell: $env:ENVIRONMENT="dev"; $env:DATABASE_URL="sqlite:///./competency.db"
uv run python -m scripts.seed
uv run uvicorn app.main:app
```

Зависимости добавляются через `uv add <пакет>` (для разработки — `uv add --dev <пакет>`),
после этого `uv.lock` нужно закоммитить.

## Веб-интерфейс

Статическая страница без сборки (`app/static`), работает поверх того же API.

- **Администратор:** назначить тест группе (выбор компетенций по видам УК/ОПК/ПК, фильтр по
  дисциплине, видно, сколько вопросов в банке), студенты группы и их логины, сводка
  результатов группы по компетенциям, экран «ПК → ОТФ» по каждому студенту, импорт
  компетенций из файлов ОПОП/РПД, банк вопросов
  (добавление, правка, удаление, фильтр по компетенции и дисциплине) и справочники:
  направления, группы, компетенции, индикаторы, дисциплины, профстандарты, ОТФ, ТФ ⇒ компетенции.
- **Студент:** мои тесты со статусом, прохождение теста, мои результаты по компетенциям и
  трудовым функциям профстандарта.

## Импорт компетенций из ОПОП / РПД

Вкладка **«Импорт»** (или `POST /import/preview` → `POST /import/apply`). Поддерживаются
`.docx`, `.xlsx`, `.pdf` и `.txt`; старые `.doc`/`.xls` нужно пересохранить.

Разбор не привязан к вёрстке конкретного вуза: из файла извлекается текст (абзацы и ячейки
таблиц, объединённые ячейки учитываются один раз), в нём ищутся коды компетенций `УК-1`,
`ОПК-5`, `ПК-2` и индикаторов в распространённых записях — `УК-1.1`, `ИУК-1.1`, `ИД-1.УК-1`,
`ИД-1 ОПК-5`, `ИДК-ПК-2.1`. Формулировкой считается текст после кода до следующего кода; если
код встречается несколько раз (таблица и перечисление «формирует компетенции УК-1, ПК-2»),
берётся самая полная формулировка. Название дисциплины берётся из строки вида
«Рабочая программа дисциплины «…»».

Перед сохранением администратор видит предпросмотр: новые компетенции и индикаторы, отличия
от того, что уже есть в базе, предупреждения (например, у новой компетенции не нашлась
формулировка — её можно вписать). При сохранении:

- создаются недостающие компетенции и индикаторы;
- формулировки существующих меняются только с флагом «Перезаписать формулировки»;
- компетенции привязываются к дисциплине (она создаётся, если её нет);
- ничего не удаляется, повторный импорт того же файла ничего не меняет.

PDF разбирается по извлечённому тексту: у сложных многоколоночных PDF порядок текста может
перемешаться, поэтому для них особенно важно проверить предпросмотр.

## Импорт студентов из выгрузки СДО

Вкладка **«Импорт» → «Студенты (выгрузка СДО)»**. Принимает CSV (UTF-8 или Windows-1251,
разделитель `,` `;` или табуляция) и `.xlsx`: выгрузку участников курса или журнала оценок из
СДО (например, Moodle), список из деканата и т.п.

- Колонки определяются по заголовкам: «ФИО» / «Имя / Фамилия» или отдельно фамилия, имя,
  отчество; группа («Группа», «Группы», «Отдел»); e-mail; идентификатор СДО («Индивидуальный
  номер», «ID number», номер зачётки) или логин; роль; образовательная программа
  («Образовательная программа», «Направление», «Специальность»). Если заголовки не узнаны,
  колонки выбираются вручную.
- Если есть колонка ролей, преподаватели и прочие не-студенты по умолчанию не отмечены.
- Студент узнаётся по идентификатору СДО, затем по e-mail, затем по ФИО в той же группе —
  без учёта порядка слов («Иван Иванович Иванов» = «Иванов Иван Иванович») и ё/е.
- Недостающие группы создаются в направлении из колонки образовательной программы (по коду
  вида 09.03.04 или названию), а без неё – в выбранном направлении; для строк без группы задаётся группа
  по умолчанию. Перевод студента в другую группу подхватывается при повторной загрузке.
- Новым студентам можно сразу создать учётные записи: логин берётся из логина СДО, e-mail или
  ФИО транслитом, пароль генерируется. Логины и пароли показываются один раз и скачиваются в CSV.
- Или учётки не создавать: студенты **регистрируются сами** («Зарегистрироваться» на странице
  входа). Студент выбирает группу, вводит ФИО полностью и задаёт пароль; ФИО сверяется со
  списком группы без учёта регистра, лишних пробелов и ё/е. Если студента нет в списке или
  учётка уже есть – понятное сообщение; подбор ФИО замедляется так же, как подбор пароля.
  Входить можно по ФИО. В списке студентов администратор видит, когда создана учётка, и
  может сбросить пароль.
- Ничего не удаляется; повторная загрузка того же файла ничего не меняет.

## Миграции

Схема БД ведётся через Alembic. Контейнер `api` применяет миграции при старте.

```bash
uv run alembic upgrade head                                  # применить
uv run alembic revision --autogenerate -m "что изменилось"   # после правки app/models.py
uv run alembic downgrade -1                                  # откатить последнюю
```

Тест `tests/test_migrations.py` и job `migrations` в CI падают, если модели разошлись
с миграциями, — то есть если забыли сгенерировать ревизию.

Тесты используют SQLite в памяти, PostgreSQL для них не нужен:

```bash
uv run pytest
uv run ruff check . && uv run ruff format --check .
```

Браузерные тесты (`tests/e2e`) проходят основные сценарии в настоящем Chromium: поднимают
сервер на копии демо-базы и кликают по интерфейсу администратора и студента. В обычный прогон
они не входят, в CI — отдельный job `e2e`:

```bash
uv run playwright install chromium   # один раз
uv run pytest -m e2e
```

Если Chromium уже установлен, можно указать его вместо скачивания: `E2E_CHROMIUM=/путь/к/chrome`.

## Безопасность

**Безопасно по умолчанию.** Без настроек приложение работает в строгом режиме `prod`:
- не запустится без своего `SECRET_KEY` длиной от 32 символов — публичного ключа «по
  умолчанию» нет, поэтому подделать токен по коду из репозитория нельзя;
- не запустится, если в базе остались демо-учётки с паролями из этого README;
- cookie сессии отдаётся только по HTTPS, включается HSTS, загрузка демо-данных запрещена.

Для разработки режим включается явно: `ENVIRONMENT=dev` (так сделано в `docker-compose.yml`).
В dev без `SECRET_KEY` генерируется случайный ключ на время работы процесса. Первый
администратор на сервере создаётся командой `python -m scripts.create_admin <логин>`.

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"   # сгенерировать SECRET_KEY
```

**Вход и сессии.**
- Пароли хранятся в виде хэша scrypt со случайной солью. Для несуществующего логина хэш тоже
  считается, поэтому по времени ответа нельзя узнать, есть ли такой пользователь.
- Веб-интерфейс держит сессию в httpOnly-cookie с `SameSite=Strict`: JavaScript её не видит,
  поэтому внедрённый скрипт не может украсть токен. Изменяющие запросы с cookie обязаны нести
  заголовок `X-Requested-With` — защита от CSRF. Внешние клиенты и Swagger работают с
  заголовком `Authorization: Bearer`.
- **Общие компьютеры.** Cookie сессии исчезает при закрытии браузера, а сама сессия
  заканчивается после 60 минут без действий (`SESSION_IDLE_MINUTES`) и продлевается при
  активности.

**Защита от подбора пароля** рассчитана на вуз, где все компьютеры выходят в интернет с одного
IP, — жёсткой блокировки нет, иначе любой студент мог бы закрыть вход одногруппнику или всему
кампусу:
- после 5 неверных паролей к логину попытки разрешены не чаще раза в 30 секунд
  (`LOGIN_SLOWDOWN_AFTER`, `LOGIN_SLOWDOWN_SECONDS`) — подобрать так пароль нереально, а
  владелец просто подождёт; подбор к одному логину не мешает остальным;
- с браузера, где владелец уже успешно входил (httpOnly-cookie `device`, 180 дней), замедления
  нет вовсе;
- потолок 300 неудач за 15 минут с одного IP (`LOGIN_MAX_FAILURES_PER_IP`) — только против
  массового перебора по многим логинам.

**Пароли.** Пароль, выданный администратором (при создании учётки, импорте или сбросе),
временный: при первом входе пользователь обязан задать свой, до этого остальной API ему закрыт.
Требования: от 8 символов, не содержит логин, не из списка самых распространённых паролей
(включая `йцукенгш`, `qwerty123` и т.п.), не только цифры короче 12 знаков. Смена или сброс
пароля завершает все остальные сеансы этого пользователя (версия токена в учётке).

**Зависимости** проверяются в CI на известные уязвимости (`pip-audit` по `uv.lock`).

**Заголовки.** Строгая Content-Security-Policy (только свои скрипты, без inline-кода),
`X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`.

**Журнал действий.** Каждый изменяющий запрос авторизованного пользователя (создание, правка,
удаление, импорт, сброс паролей) записывается: кто, когда, что, результат, IP. Админ видит
журнал во вкладке «Журнал» и через `GET /audit`.

**Удаление данных.** Студента с результатами тестов удалить нельзя: пропали бы данные
отчётов. Его можно перевести в другую группу. Удаление студента без результатов удаляет и его
учётную запись.

## Роли и API

Авторизация: веб-интерфейс — httpOnly-cookie, API — `Authorization: Bearer <token>`; токен
выдаёт `POST /auth/token` (OAuth2 password flow). Три роли:

- **admin** – справочники, банк вопросов, сборка и назначение тестов, отчёты, пользователи;
- **teacher** – преподаватель или сотрудник кафедры: видит закреплённые за ним дисциплины
  учебного плана, сколько вопросов по каким компетенциям нужно разработать, составляет их
  (только по своим дисциплинам и их компетенциям) и выгружает ФОМ в Word;
- **student** — только свои назначения, прохождение тестов и свои результаты. Учётка студента
  привязана к записи в списке студентов, поэтому `student_id` берётся из токена, а не из запроса.

| admin | `POST` | `/import/students/apply` | Создать/обновить студентов, группы и учётки |
| student | `GET` | `/me/assignments` | Назначенные мне тесты |
| student | `POST` | `/me/attempts` | Начать попытку (вопросы без правильных ответов) |
| student | `POST` | `/me/attempts/{id}/submit` | Сдать ответы, получить балл |
| student | `GET` | `/me/reports/competencies` | Мои результаты по компетенциям |
| student | `GET` | `/me/reports/labor-functions` | Мои закрытые ОТФ / ТФ |
| student | `GET` | `/me/reports/profile` | Мои уровни для «розы ветров» |
| teacher | `GET` | `/teacher/disciplines` | Мои дисциплины: квоты и прогресс по компетенциям |
| teacher | `GET` | `/teacher/disciplines/{id}/fund.docx?key=` | ФОМ своей дисциплины в Word |
| teacher | `POST/GET/PUT/DELETE` | `/questions` | Вопросы только своих дисциплин |

`PUT` заменяет запись целиком. Удаление записи, на которую ещё ссылаются (группа со
студентами, компетенция с вопросами и т.п.), возвращает `409` с причиной. Профстандарт и ОТФ
удаляются вместе со вложенными ОТФ и ТФ.

Вопрос, который уже вошёл в собранный тест, защищён: по нему могут быть ответы студентов, поэтому
у него можно менять только формулировки, индикатор и дисциплину, а удалить его нельзя.

## Структура

```
app/
  models.py              модель данных
  schemas.py             Pydantic-схемы запросов и ответов
  security.py            хеширование паролей (scrypt) и JWT
  api/                   роутеры FastAPI: HTTP, права доступа, простой CRUD
  services/
    common.py            get_or_404, save, update_fields, delete_or_conflict
    testing.py           сборка тестов, назначение, прохождение и проверка
    questions.py         правила редактирования банка вопросов
    reports.py           результаты по компетенциям и ТФ профстандарта
    files.py             чтение загруженных файлов (docx, xlsx, pdf, csv)
    competency_import.py импорт компетенций из ОПОП / РПД
    student_columns.py   таблица студентов: колонки и разбор строк (без БД)
    student_import.py    импорт студентов: сопоставление, предпросмотр, сохранение
    accounts.py          логины и пароли студентов
  static/                веб-интерфейс без сборки (ES-модули)
    js/core.js           DOM, запросы к API, сессия, навигация
    js/main.js           вход, меню по ролям, тема
    js/student.js        кабинет студента
    js/admin/*.js        экраны администратора, по файлу на экран
migrations/              ревизии Alembic
scripts/                 точка входа контейнера, создание администратора, демо-данные
deploy/                  Caddyfile, резервное копирование и восстановление
docs/deploy.md           развёртывание и эксплуатация
docker-compose.yml       локальный запуск (dev)
docker-compose.prod.yml  продакшен
tests/
```

Правило слоёв: роутер отвечает за HTTP и права, а простое создание и изменение записи делает
через `save` / `update_fields`. Всё, где есть правила предметной области или несколько шагов
(сборка теста, проверка ответов, импорт, ограничения на правку вопросов), — в `services/`.
